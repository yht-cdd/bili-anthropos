# 模型降级切换

> 一份开关，管住三套互相不知道对方死活的配置。

## 为什么需要它

2026-10-31 早上发现：魔搭账户返回 `insufficient balance`，四个模型全挂。

但她的模型配置是**三套独立**的：

| 用途 | 配置在哪 | 出问题时的表现 |
|---|---|---|
| 主模型（大脑） | `/root/.config/opencode/opencode.json` + bridge 的 `OC_MODEL` | 她回不出话，看起来像「不想理人」 |
| 子代理 | `config/agent-models.json` 的 ladder | 派活全部失败 |
| 看视频 / 看图 | `scripts/vision.mjs` 的 `CHAIN` | 视觉调用报错 |

三套各自挂在同一个 key 上，一处额度用完，三处同时哑掉，
**但没有一处会告诉另外两处**。这就是那天她沉默的直接原因。

## 怎么用

```bash
node scripts/model-mode.mjs status      # 现在什么模式
node scripts/model-mode.mjs set auto    # 切回魔搭优先（0 点日切自动做）
node scripts/model-mode.mjs set brocod  # 降级到 brocod（额度报错时自动做）
```

`set` 一次改**五**个地方：

1. `config/model-mode.json` —— 模式状态（`vision.mjs` 读它决定链顺序）
2. `/root/.config/opencode/opencode.json` 的默认 `model`
3. `/root/.opencode.env` 的 `OC_PROVIDER_ID` / `OC_MODEL_ID`
4. `config/agent-models.json` 的 ladder 顺序（没有这个 provider 会自动补一条）
5. **把已有会话改绑过去**（调 opencode API）

第 5 条最容易漏：`opencode.json` 的 `model` 只影响**新建**会话。
已有会话会一直绑着创建时的模型，所以会出现「默认模型已经换了，
但 Web UI 里那个会话还指着死模型，发一句挂一句」。

## 三种模式

| | `auto`（常态） | `brocod`（降级） | `amd`（视觉备用） |
|---|---|---|---|
| 主模型 | `modelscope/Qwen/Qwen3.8-Flash-Next` · `high` | `brocod/deepseek-v4.1` · `high` | `amd/Qwen3.8-Flash-Next` · `medium` |
| 上下文 | 1M | 1M | **262k** |
| 子代理阶梯首位 | 魔搭 | brocod | AMD |
| 视觉链首位 | 魔搭 | AMD | AMD |

### 为什么降级目标是 brocod 而不是 AMD

实测卡在这里：**AMD 的 Qwen3.8-Flash-Next 只有 262k 上下文，
而她 2026-10-31 的主会话已经是 329k tokens。**

```
level=WARN provider rejected the request as too long; compacting
  model.providerID=amd message="The input (329407 tokens) is longer than the model's context"
```

塞不进去，请求直接被拒。表现就是「3 秒就结束、outcome=failed、正文是上一轮的残留」。

brocod 的 `deepseek-v4.1` 是 1M 上下文，塞得下，速度也一样（3 秒）。

所以：

- **主大脑** → brocod（1M）
- **看视频/看图** → AMD（图小、上下文用不完，实测 2.4-3.1 秒，识别准确）

## 自动切换的两端

| 触发 | 动作 | 代码位置 |
|---|---|---|
| 某轮失败，`describeFailure` 判成 `quota` | 切 `brocod` + 改绑当前会话 + 重试 | `bili-bridge.mjs` → `runTask` |
| 00:00 固定日切 | 切回 `auto` + 改绑当前会话 | `bili-bridge.mjs` → 到点分支 |
| bridge 启动 | 把会话改绑到当前模式的模型 | `bili-bridge.mjs` → 启动自检 |

判定 `quota` 的依据：

```
status === 429 或 消息里出现 quota / insufficient / balance / rate-limit / 额度 / 余额 / 用量
```

## 实测（2026-10-31）

```
① 切 auto → 模拟任务
   ↻ 这一轮失败了（quota: 模型额度用完了（429 / 余额不足）），按约定重试一次
   🔀 模型模式 → brocod：brocod/deepseek-v4.1
   🔧 已把会话模型改绑到 brocod/deepseek-v4.1
   ✅ 重试成功 → 「在线」

② 切 brocod
   会话改绑       : 10 个改绑到 brocod/deepseek-v4.1
   子代理阶梯     : 新增 brocod/deepseek-v4.1 并放到首位

③ 在 Web UI 那个会话里发一条
   会话模型: {"id":"deepseek-v4.1","providerID":"brocod"}
   outcome: succeeded  3.0s
   正文: "在的"

④ 子代理
   「我跑在 deepseek-v4.1 上，由 brocod 提供接入。」
```

速度对比（同一会话、同一问题）：

| 模型 | 结果 | 耗时 |
|---|---|---|
| `brocod/deepseek-v4.1` | succeeded | 3.0s |
| `amd/Qwen3.8-Flash-Next` | succeeded（会话小的时候） | 3.0s |

## 踩过的坑

1. **`variant` 不能跨厂商照抄**。`high` 在 DeepSeek 系能用，在 AMD 的 Qwen3.8 上不合法
   （只接受 `none` / `low` / `medium` / `xhigh`）。
2. **改默认模型 ≠ 改会话绑定**。这是当天「没自动切换」的直接原因 ——
   默认值改了，但那个会话还绑着魔搭，Web UI 手动发一句照样挂。
3. **Web UI 手动对话不经过 bridge**，所以 bridge 的自动降级管不到它。
   只有把会话本身改绑过去，手动聊天才会跟着好。
4. **降级不等于换会话**。只 `rebindModel` 改绑模型，会话记忆不动 —— 换会话会丢记忆。
5. **已经在目标模式还报额度错，就不要再切**，否则会来回抖动。
   代码里用 `readModelMode() !== "brocod"` 挡了一下。
6. **opencode 当前版本不认 `attachment` / `reasoning`** 这两个字段
   （日志里 `omitted unsupported legacy setting`），输入类型要用 `modalities` 表达。
