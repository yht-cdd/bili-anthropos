### 扩写动画类任务时的引用规则

1. **读取对应 HTML 文件**：根据动画类型读取 `animations/` 中对应文件，提取关键的技术实现（CSS keyframes、SVG 结构、JS 注入逻辑）
2. **提炼核心参数**：从参考文件中提取「精确数值」——动画时长（如 `1.6s`、`2.4s`）、缓动曲线（如 `cubic-bezier(0.28, 0.84, 0.42, 1)`）、颜色（HEX）、字号、字体、描边宽度
3. **避免照搬**：提取参考文件的「动画原理」和「数值规格」，但必须根据用户的具体文案/品牌/风格重新定制内容
4. **注入扩写提示词**：在扩写产物中，将参考文件中的技术规格写入「动画时序表」章节，并标注参考来源文件名
5. **跨分类参考**：一个动画任务可能融合多种效果（如「霓虹+波浪」= 07-霓虹辉光 + 03-彩虹波浪），可同时引用多个参考文件

## 工作流程

### 步骤 1：解析简短提示词

识别 5 个要素，缺失的即为待澄清项：

1. **任务类型**：网站 / 前端组件 / CLI 工具 / 脚本 / 算法库 / 移动端 / 配置任务 / **全栈 Web 应用**
2. **核心功能**：必须做什么（名词化，列出清单）
3. **交付形式**：单文件 / 多文件项目 / 压缩包 / 可运行服务 / **Next.js 全栈项目（直接改项目文件）**
4. **技术栈线索**：提到的框架、语言、库；未提到即待定
5. **验收方式**：怎么算完成（截图、测试命令、运行结果、`npm run build`）

> **模板选择规则**：若任务类型为「全栈 Web 应用」或技术栈包含 Next.js/React/PostgreSQL/Drizzle，自动使用 `references/prompt-template-nextjs.md` 模板，跳过「视觉规格」「动画时序」章节，改用「数据层/页面/API 规格」。

### 步骤 2：先问再扩写（必须）

用 question 工具一次性确认关键缺口，每个问题给出推荐选项（第一个选项标注「(推荐)」）。默认问 3-5 个：

- **技术栈**：询问用户偏好；若用户不指定，默认无限制并注明
- **交付物形式**：如「可运行项目+目录树」「单 HTML 文件」「npm 包」「Next.js 全栈项目」
- **视觉/风格**：如「终端风/深色」「玻璃拟态」「无特别要求」「简洁后台」——若无要求，扩写时自行定义并写明
- **是否已有参考**：参考网站 URL、截图、既有代码位置
- **范围与禁忌**：明确不要什么（如「不要后端」「不要外部资源」「不要 npm 构建」）——若用户未提禁忌，默认无限制

> **Next.js 全栈任务额外询问**（若模板选择为 Next.js）：
> - **数据实体**：需要哪些数据库表，各自字段
> - **页面清单**：需要哪些页面（列表/详情/表单/仪表盘等）
> - **是否需要**：登录/角色/外部 API（哪个）/文件上传
> - **UI 风格**：简洁后台 / 深色 / 营销落地页

> 若用户说「不用问，直接写」，跳过步骤 2，全部采用合理默认并在输出头部声明假设清单。

### 步骤 3：按模板逐节扩写

加载对应模板骨架，逐节填充。扩写时遵守第 4 节「13 要素扩写规则」。

**模板选择规则**：
- 通用任务（单 HTML / 动画 / 前端组件 / CLI 工具）：使用 `references/prompt-template.md`
- **全栈 Web 应用**（Next.js + TypeScript + Tailwind + PostgreSQL + Drizzle）：使用 `references/prompt-template-nextjs.md`
- 判断依据：任务类型为「全栈 Web 应用」或技术栈包含 Next.js/React/PostgreSQL/Drizzle 关键词

### 步骤 4：编排子代理分工（必须）

按第 4 节要素 13 与第 5 节「Agent 平台适配」，把任务拆解为可并行子任务，写入「子代理编排」章节，必须使用 `@general` 语法分配子代理完成各项任务。子任务按文件/模块划分，写明接口契约与合并规则。

> **Next.js 全栈项目**的典型拆分方式：
> - `@general`：实现 Drizzle Schema + 种子数据，规格见第 2 节，输出到 `src/db/schema.ts`
> - `@general`：实现 API 路由，规格见第 4 节，输出到 `src/app/api/.../route.ts`
> - `@general`：实现页面 + 组件，规格见第 3 节，输出到 `src/app/.../page.tsx` 及 `src/components/`
> - `@general`：实现 Server Actions / 表单处理，规格见第 3.2 节，输出到 `src/app/.../actions.ts`
> - 串行依赖：API 路由依赖 Schema 先行，页面依赖 API 先行

### 步骤 5：注入精准代码示例

在核心逻辑、数据结构、验收相关章节，必须插入可落地的代码/公式/命令块。见第 6 节代码示例类型清单。

### 步骤 6：写入文件

- 保存路径：`.agents/prompts/{slug}.md`（slug 为任务英文短名，如 `blackhole-website.md`；目录不存在则创建）
- 若用户指定了路径，按用户路径保存

### 步骤 7：自动验证（必须）

写入文件后必须运行自动校验脚本，不能跳过：

```powershell
powershell -ExecutionPolicy Bypass -File ".agents/skills/prompt-expander/scripts/validate-prompt.ps1" -Path ".agents/prompts/{slug}.md"
```

- 返回码 0 = 全部通过；返回码 1 = 存在 FAIL 项
- 有 FAIL 项时必须修复后重新校验，直至返回码 0 才算完成扩写
- WARN 项不阻塞，但输出时须向用户说明
- 脚本检查项见第 7 节「自动验证」；脚本本身不可用（如平台非 Windows）时，退化为逐条人工执行第 8 节「质量红线」自检清单

完成后回复：文件路径 + 章节结构摘要 + 关键假设/待澄清项列表 + 自动校验结果（几项 PASS / FAIL）。

## 13 要素扩写规则

每个要素给出「简短表述 → 超详细表述」的转换手法。禁止只是加形容词；每一项都必须落到可执行、可验收的具体值。

> **注意**：当使用 Next.js 全栈模板时，要素 6（精确数值）、7（公式级细节）、10（动画时序表）通常不适用，应用「数据层 Schema 定义」「API 规格」「页面数据流」替代。要素 11（响应式与错误恢复）简化为 Tailwind 断点 + 构建错误处理。

### 1. 角色注入与责任界定

- 简短：「做一个游戏」
- 超详细：「你是一名资深游戏前端工程师、动画设计师和性能优化专家。请从零制作…。你不会收到任何原始代码文件，以下规格是唯一实现依据。最终必须是真正可玩的完整成品，任何把占位逻辑当完成结果的做法均不合格。」
- 规则：按任务领域堆叠 2-3 个具体专业头衔；随后明确「唯一依据、不得索要源码」或「可参考 XX 但不得照搬」的边界。

### 2. 边界与禁令清单

- 简短：「别用那些花哨的东西」
- 超详细：「技术栈无限制，模型可自由选择任何框架、库、工具链。扩写时向用户确认技术栈选型即可，不得擅自替用户做限制。」
- 规则：扩写时不再预设技术禁令，而是通过 question 工具向用户确认技术栈偏好。用户未指定时，默认采用「自由选择，无限制」并在输出头部声明。

### 3. 交付物与目录树

- 简短：「给我一个完整项目」
- 超详细（代码块）：
  ```
  index.html
  css/style.css
  js/main.js
  js/shaders.js
  vendor/three.module.js
  audio/main.mp3
  ```
- 规则：目录树必须逐文件精确列出；写明运行方式（静态服务器 / npm run dev / 直接双击）。

### 4. 技术栈锁定

- 简短：「用前端技术做」
- 超详细：「技术栈无限制，可自由选择任何框架/库/工具链。向用户确认技术栈选型，用户未指定时默认采用当前主流方案（如 React + Vite）并注明。」
- 规则：不得预设技术禁令；扩写时通过 question 向用户确认技术栈偏好；用户未指定时自行选择合理方案并在头部声明假设。

### 5. 分章节编号规格

- 简短：「做几个页面，有这些功能」
- 超详细：编号体系「【一、…】→【二、…】…」每章下 1. 2. 3. 条，每章 5 条以上，总字数对标范式（约 150 行 markdown，短任务不低于 60 行）。
- 规则：章节按「架构 → 核心逻辑 → 视觉 → 交互 → 数据 → 错误处理 → 验收」顺序组织；一条规格只讲一件事，避免「并且」混装多条规格。

### 6. 精确数值

| 模糊表述 | 超详细表述 |
|---------|-----------|
| 「深色背景」 | 「主背景 `#070605`，模块背景近黑 `#000000`/`#050505`，禁止蓝灰大底」 |
| 「标题醒目」 | 「主标题 34px/700 字重/letter-spacing .42em/纯白 + 青色双层发光；副标题 11px/.30em/琥珀」 |
| 「动画流畅」 | 「5.2 秒 keyframes：0% opacity0/scale1.06/blur8px；25% opacity1/scale1/blur0；80% 保持；100% opacity0/scale.99」 |
| 「等一会儿再消失」 | 「intro 后 2.5 秒出现提示条，持续 10 秒，900px 以下视口隐藏」 |
| 「适当调整」 | 「默认 FOV 44°、near .01、far 200；`uDopMax` 默认 1.85、clamp 到 .50…uDopMax」 |
| 「好几个参数」 | 「21 项参数，每项带 range、step、默认值表：GEODESIC STEPS 60–600 /10 默认随质量档 200/320/460」 |

- 规则：颜色给 HEX + 用途；字号给 px + 字重 + 字距；间距给 px；动画给 keyframes + 毫秒表；参数给 范围/步长/默认值 三件套；缺失值用户未指定时由你定义精确默认值并写明。

### 7. 公式级细节

核心算法、物理/数学逻辑必须给出可编码的公式，直接用代码块写成 shader/伪代码：

```glsl
// 光子加速度（Schwarzschild 零测地线）
h   = cross(pos, vel);
h2  = dot(h, h);
r2  = r * r;
acc = -1.5 * RS * h2 / (r2 * r2 * r) * pos;
// 自适应步长
dt  = max(.012, r * mix(.02, .06, smoothstep(6., 20., r)));
```

- 规则：公式中的每个符号都要说明含义和单位；写明 clamp 范围与防 NaN 下限；禁止只写「用物理公式」不写公式本体。

### 8. 精准代码示例

必须给出真实 API 签名、真实参数、可运行的代码/命令。见第 5 节类型清单。

### 9. 状态机 / 事件 / 数据字段定义

- 简短：「记录用户操作」
- 超详细：事件列表 + 字段表：
  ```
  事件：keyTravel → linkage → impact → typebarRest → escapement → bell → clash → changed
  每个字形记录：char / code / page / line / col / timestamp / inkOpacity / xJitter / yJitter / overstrikeCount / history / viaUnicodeAdapter
  规则：每页 44 行、每行 72 格；第 66 列触发边距铃；页码满时 pageFull 阻止输入
  ```
- 规则：状态机要写清状态列表 + 转移条件 + 边界行为（满/空/非法输入时怎么办）；字段表给出字段名 + 含义 + 单位。

### 10. 动画时序表

- 简短：「有机械联动感」
- 超详细（表格或编号时序）：
  ```
  1. 键帽下沉（0-35ms）→ 2. 键杆绕枢轴运动 → 3. 连杆牵引（20ms 事件）
  4. 字杆上扬（20-100ms）→ 5. 色带提升器抬起（55ms 起）→ 6. 字模撞击（100ms 事件）
  7. 纸面应用字符 → 8. 逃逸释放（120ms）→ 9. 滑架移动（110ms）→ 10. 字杆复位（210ms）
  ```
- 规则：时序用毫秒精确到事件触发点与结束点；多元素联动用编号顺序链；冲突/快速连续触发要有明确的碰撞处理规则。

### 11. 响应式与错误恢复

- 简短：「手机也能用，别崩」
- 超详细：「720px 以下：主标题 22px、deck 宽 210px/right 20px；390×844 不重叠。捕获 shader compile/link 错误并显示『降低质量/重试』覆盖层；处理 webglcontextlost/restored、localStorage 异常、音频 404；页面 hidden 时暂停渲染；不能把用户留在纯黑页面。」
- 规则：列出 2-3 个主流断点的具体数值行为；列出必须捕获的至少 3 类错误及降级策略；明确「不允许出现」的失败形态。

### 12. 硬性验收清单

- 简短：「做完检查一下」
- 超详细（编号 + 可执行方式）：
  ```
  1. 在 POSTER/EDGE-ON/POLAR/CLOSE PASS 分别截图，验证距离/倾角精确为 24/38°、26/6°、28/82°、9/14°；
  2. 完整运行 88 秒电影闭环，8 段连接无跳变；
  3. 用 Playwright 访问 `?shot&cam=poster&q=cinematic` 截图，收集 pageerror 与 console.error；
  4. 三档质量的实际 steps 和 DPR 与 HUD 一致；
  5. 完成判定：实时、科学结构可信、电影级且完整交互；只实现黑球圆盘的结果不合格。
  ```
- 规则：每条验收必须可验证（数值对比/命令执行/截图检查）；必须给出「什么算不合格」的反面判定；最终要求提供启动命令、目录树、验证结果。

### 13. 子代理编排（多智能体分工）

扩写的提示词必须包含「子代理编排」章节，使用 `@general` 语法把各项任务分配给子代理。这是必填要素，不是可选项。

- 简短：「任务有点大，分开做」
- 超详细（扩写时写入提示词的完整段落）：
  ```
  【多智能体分工】
  1. 本任务必须使用 @general 分配子代理完成各项任务，禁止主代理单线程包办全部实现；
  2. 子任务拆解为 N 个可并行单元，按「文件/模块/独立功能」切分，例如：
     @general：实现 X 模块，规格见第 X 节，输出到 src/xxx.ts，接口签名必须符合第 X 节契约；
     @general：实现 Y 模块，规格见第 X 节，输出到 src/yyy.ts；
     @general：编写 Z 测试并跑通 `npm test`；
  3. 探索型任务（查代码、找文件、确认 API）使用 explore 类子代理完成；
  4. 串行约束：存在依赖关系的子任务必须标注「等待前置子代理完成后再启动」；
  5. 接口契约先行：并行前必须先确定目录树、模块签名、数据格式与通信约定，子代理按契约实现；
  6. 主代理职责：汇总各子代理产出、交叉验证契约一致性、统一代码风格、运行最终验收。
  ```
- 规则：
  - 子任务拆解粒度：一个子代理负责一个文件/一个模块/一个独立功能，禁止把整个项目丢给一个子代理
  - 必须给出「并行策略」：哪些可并行、哪些必须串行（用「等待前置」标注依赖）
  - 必须给出「合并与验收」：主代理如何整合、验证各子代理产出，防止接口对不上
  - 子代理分配指令必须逐条以 `@general：` 开头写清：任务内容 + 规格章节引用 + 输出路径 + 接口契约
  - 任何多文件项目（≥3 个文件）都必须编排子代理；单文件小脚本可豁免但需注明

## Agent 平台适配

扩写提示词中必须适配目标 agent 平台的子代理机制。用户未指定平台时，默认 opencode 语法并在提示词头部注明「本提示词按 opencode 多智能体运行」。

| 平台 | 子代理语法 | 说明 |
|------|-----------|------|
| opencode | `@general`：任务内容 | 对应 task 工具 subagent_type=general，用于实现/执行类任务；主代理负责整合与验收 |
| opencode | `@explore`：探索内容 | 对应 subagent_type=explore，用于只读代码探索、定位文件、确认 API |
| **Web AI Agent** | `@general`：任务内容 | **同 opencode 语法，但子代理可直接在项目内读/写/改/删文件、安装依赖、运行构建。适用于 Next.js 全栈项目。** |
| codex | 等价机制：task 工具 + 自定义 agent | 语法类似 `@agent-name：任务内容`；若目标平台是 codex，扩写时把 `@general` 替换为对应 agent 名并在头部声明 |

适配规则：

1. 扩写时先判断目标平台（opencode / codex / 其他 agent），在提示词头部写明平台声明段：
   ```
   运行平台：{opencode | codex | 其他}
   多智能体约定：本提示词内所有 `@general：` 子代理指令必须实际分发执行，主代理不得自行代劳。
   ```
2. 子代理指令默认用 `@general` 语法；目标平台为 codex 时，用等价 agent 语法并统一替换。
3. 平台无关原则：子任务内容本身必须平台中立（只说「做什么、按哪节规格、输出到哪」），只有语法前缀随平台切换。
4. 主代理职责固定不变：汇总、契约校验、风格统一、最终验收——这三项必须留在主代理，不得下发给子代理。

## 自动验证

扩写产物通过 `scripts/validate-prompt.ps1` 自动校验，替代纯人工核对。脚本检查项（对应质量红线）：

| # | 检查项 | 判定 |
|---|--------|------|
| 1 | 总行数门槛 | ≥150 大任务 / ≥60 小任务 |
| 2 | 模糊词检测 | 数量/程度/时间模糊词、主观评价词、孤立「流畅/高性能」零命中 |
| 3 | 必填要素章节 | 角色注入、目录结构、技术栈禁令、状态机、验收、错误恢复各出现 |
| 4 | 精确数值抽查 | HEX 色值、px 数值、动画时长/keyframes 各至少一处（Next.js 模板可放宽） |
| 5 | 平台声明段 | 含「运行平台」或「多智能体约定」或 @general/@explore |
| 6 | @general 指令数 | ≥2 条；单文件任务须注明豁免 |
| 7 | explore 子代理 | 多文件任务须提及（WARN 级） |
| 8 | 占位符残留 | 无未替换的 `{...}` 占位符 |
| 9 | **Next.js 检测** | 若任务含 Next.js/PostgreSQL/Drizzle 关键词，须使用 `prompt-template-nextjs.md`（WARN 级） |

脚本输出 PASS/FAIL/WARN 报告；FAIL 必须修复后重跑，返回码 0 方可交付。

## 质量红线（自检清单）

自动验证通过后，仍须人工复核以下不可自动化的条目：

- [ ] 每章至少 5 条规格，章节按固定顺序组织，编号体系完整（【一、】内 1. 2. 3.）
- [ ] 核心算法有公式或伪代码，符号有解释，边界有 clamp
- [ ] 子代理分配指令均含「任务内容 + 规格章节引用 + 输出路径 + 接口契约」四要素
- [ ] 主代理职责（汇总、契约校验、验收）未下发到子代理
- [ ] 有响应式断点数值 + 错误捕获清单
- [ ] 验收清单每条可验证（数值对比/命令执行/截图检查）+ 反面判定 + 完成判定
- [ ] 开头有角色注入，结尾有交付要求（启动命令、目录树、验证结果）

### Next.js 全栈模板额外检查

- [ ] Drizzle Schema 表定义包含字段/类型/关联/索引，无遗漏
- [ ] API Route 有完整请求/响应格式定义，含状态码
- [ ] 页面数据流清晰（Server Component / API / Server Action 选择合理）
- [ ] 明确标注了 `npx drizzle-kit push` 同步步骤
- [ ] 验收清单包含 `npm run build` 构建验证
- [ ] 数据库操作使用真实 `import { db } from '@/db'`，无 mock 数据
